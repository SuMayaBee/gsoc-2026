The work at a glance

Thirty-one upstream contributions, across the whole product path.

During GSoC 2026, I worked on Panel Live Server, a Python application and MCP server that lets people and AI assistants create, display, inspect, and refine Python visualizations and Panel applications in real time.

My work focused on making the tool more useful in real MCP clients, more reliable across Python environments, less expensive in model context, easier to configure, and easier to install and understand. I contributed across the MCP server, screenshot pipeline, rendered-result interface, command-line interface, tests, documentation, and project communication.

Technical innovations and major contributions

The workstreams behind the final project.

The details below are the full account of the work from my final report, organised by the part of Panel Live Server that each contribution improved.

01 / FEEDBACK

Visual feedback became part of the AI workflow

The most important change was treating a screenshot as feedback for the assistant, rather than as a static export for the user. Before this work, an assistant could create a visualization with show(), but it could not see the final rendering. To check its own result, it had to show an unfinished chart or dashboard to the user, screenshot it, revise it, and then show a second version.

In PR #51, the screenshot tool gained the ability to accept Python code directly, along with a name and rendering method. The server stores the result as a temporary draft, renders it, and returns the image to the assistant. The draft is not put into the normal visualization feed. Once the assistant is satisfied, it can promote the same validated draft through show(draft_id=...) instead of recreating it.

This lets the assistant notice clipped labels, unsuitable chart types, unreadable legends, missing titles, crowded layouts, or a dashboard that does not fit in the initial viewport before the user sees it. Earlier, PR #12 renamed the two rendering choices from jupyter and panel to inline and server, making the screenshot path clearer for real Panel apps.

02 / PANEL APPS

I designed the screenshot system around real Panel applications

Panel Live Server supports both simple inline results and running Panel server applications. The screenshot feature therefore has to handle more than one static chart. It starts a local Panel view when necessary, uses Playwright Chromium to capture the rendered browser output, and returns either one image or a labelled set of images.

For PR #61, I added behaviour for dashboards that are taller than a browser window and dashboards with more than one page. This matters when the first viewport shows only a title, filter, or first tab. The implementation supports Panel Tabs and common user-built page switchers, with targeted unit tests and browser UI tests.

  • PR #17 introduced the screenshot MCP tool.
  • PR #20 made browser installation a supported CLI operation for installed PyPI, uv, pip, and Pixi users.
  • PR #61 added full-scroll and multi-page capture, including reporting when content remains outside the capture.
03 / CONTEXT COST

I measured model-context cost and changed the design

Claude Desktop could not display a localhost iframe because of its content security policy. PR #13 introduced an inline HTML fallback using iframe.srcdoc. It allowed charts to appear inside Claude Desktop and gave interactive applications a browser-link fallback.

Later, PR #46 added payload token reporting. It showed that sending a complete rendered HTML page to the model was expensive and generally not useful. For a simple chart, the embedded page could use around 14,000 tokens, compared with around 275 tokens for a normal result. In PR #47, I used that evidence to replace the embed with an explicit Open in browser action for Claude Desktop and Cowork. Cursor and VS Code remain unchanged.

04 / CORRECTION

I changed failures into a correction loop instead of a dead end

In PR #24, I merged the old two-step validate() then show() interaction into show(). The server now validates automatically before rendering. If validation or rendering fails, the tool returns a concise retry payload and the result interface enters a “Refining visualization…” state.

The server does not independently rewrite a user’s code. It turns a failure into structured feedback that the calling assistant can act on. Combined with the screenshot draft loop, this gives an MCP client two complementary ways to improve an answer before presenting it: code and runtime feedback when execution fails, and visual feedback when execution succeeds but the result is not good enough. PR #35 also added a concise error summary and a collapsible, safely inserted traceback using textContent.

05 / RELIABILITY

I made cross-environment execution reliable

A fixed default port caused a subtle failure when users had more than one Python environment. A command from one environment could reuse an existing server on the shared port even if that server belonged to another environment. The visualization then ran with the wrong installed packages.

In PR #42, I made the default Panel port deterministic per Python interpreter. The same environment can still reuse its own running server, but another environment receives a different port. PANEL_LIVE_SERVER_PORT remains an override. I also fixed a Bokeh concurrency issue in PR #49 by giving background validation an isolated temporary document through Panel’s per-thread state. PR #59 restored package checks by removing importlib from the blocked-import list.

06 / INTERFACE

I improved the rendered-result interface

  • PR #21 increased default iframe height and changed the default zoom to 75 percent.
  • PR #35 added a concise error summary and safely inserted traceback.
  • PR #36 added View Code with copy and return-to-visualization controls.
  • PR #39 added drag-to-resize support for the visualization iframe.
  • PR #40 added Python syntax highlighting to the code view.
07 / PROMPTS

I made AI instructions configurable

In PR #52, I added pls mcp --prompts, allowing users and teams to provide a JSON file with custom instructions. The initial version supported library-selection and output guidance, with append and replacement behaviour.

In PR #54, I expanded this to cover all instruction sections: introductory text, workflow, file policy, rendering guidance, errors, and screenshot guidance. Default behaviour remains unchanged when no custom prompts file is supplied.

08 / INSTALL

I improved MCP installation and client support

PR #67 added pls install <client> for Claude Desktop, Cursor, VS Code, and Claude Code. The command finds the active pls executable and writes the appropriate MCP configuration while preserving existing settings.

In PR #71, I expanded this from four to fourteen supported clients: Windsurf, Cline, Junie, Gemini CLI, Google Antigravity, Kiro, GitHub Copilot CLI, Kilo Code, OpenAI Codex CLI, and Mistral Vibe. The work handles JSON, JSONC, and different TOML shapes where necessary, preserves user-owned fields such as environment variables and timeouts, and is idempotent when run twice.

09 / QUALITY

I improved performance and code-quality enforcement

PR #15 removed redundant validation from the MCP display path. In PR #55, I measured lazy imports across source and tests. Imports with no meaningful startup cost moved to module level, while expensive imports such as Panel, Bokeh, Pandas, Playwright, and server modules remained lazy.

PR #69 enabled Ruff’s PLC0415 rule so non-top-level imports are visible during linting. In PR #72, I followed review feedback by allowing grouped imports where they improve readability, removing a temporary lint exception, and applying the formatting consistently across the codebase.

10 / DOCS

I improved documentation and contributor guidance

Documentation was continuous work. I wrote and revised setup, installation, architecture, MCP, and contributor documentation in PR #14, PR #16, PR #19, PR #32, PR #65, and PR #66. This covers setup for multiple clients, MCP tools, cross-platform guidance, server configuration, deployment, custom AI instructions, troubleshooting, and HoloViz development skills.

I also wrote the public Panel Live Server blog post. The accompanying HoloViz blog PR #101 was merged, explaining the project to a wider audience and complementing the repository documentation.

Two decisions that changed the result

Deep dives: visual review and measured context cost

A private draft turns a screenshot into feedback

The important part of the screenshot workflow is that it does not put an unfinished result into the user’s normal feed. The assistant can render a draft, see the final browser output, decide whether it needs another pass, and promote the same validated draft only after it is satisfied. This avoids the old “show, screenshot, fix, show again” sequence.

BeforeUnfinished result shown to the user before the assistant can inspect it.
AfterAssistant reviews a private draft and the user sees one intentional result.

Compatibility is not enough when context cost is too high

The inline HTML solution fixed Claude Desktop’s localhost iframe limitation, but the measurements in PR #46 made the trade-off concrete. A complete rendered HTML page was around 14,000 tokens for a simple chart versus around 275 tokens for a normal result. Replacing it with an explicit browser action made the feature more sustainable in real conversations.

Challenges and lessons learned

The real behaviour was the work.

The Claude Desktop iframe limitation taught me that MCP clients can have materially different rendering restrictions even when they use the same server. The inline HTML workaround solved the visual problem, but token measurements showed that it was too expensive. Removing the embed for affected clients was a better outcome for practical use.

The environment-port and Bokeh-document fixes taught me that local development assumptions do not always hold when users run multiple environments, long conversations, or background validation. These issues were not obvious from the happy path, so I focused on reproducing the actual failure mode and adding targeted tests where possible.

I also learned that installation UX is part of the product. Supporting many MCP clients is not only a matter of writing JSON. Clients use different paths, configuration schemas, environment variables, TOML or JSON formats, and behaviours for existing settings. The installation work therefore emphasizes preserving existing configuration, idempotency, and tests for each format.
