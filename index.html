The project in one line

From “run this code” to “check the result first.”

Panel Live Server now lets an assistant render a private draft, inspect a screenshot, refine it when needed, and show the validated result only when it is ready.

MCPPanelPlaywrightPython

What I set out to improve

Useful in real clients, not only on the happy path.

I worked across the MCP server, screenshot pipeline, rendered-result interface, command-line setup, tests, documentation, and project communication.

The goal was practical: reduce friction for people using many different MCP clients, make rendering reliable across Python environments, and make the assistant’s output easier to inspect before a user sees it.

A visual feedback loop

The screenshot feature is not just an export button.

This is the central workflow I introduced. It gives the assistant a practical way to spot layout problems such as clipped labels, crowded dashboards, unsuitable chart types, or missing titles before publishing a result.

2.1 / VISUAL FEEDBACK

Visual feedback became part of the AI workflow

The most important change in my work was treating a screenshot as feedback for the assistant, rather than as a static export for the user. Before this work, an assistant could create a visualization with show(), but it could not see the final rendering. When it needed to check its own result, it had to show an unfinished chart or dashboard to the user, screenshot it, revise it, and then show a second version.

In PR #51, I changed that workflow. The screenshot tool can accept Python code directly, along with a name and rendering method. The server stores the result as a temporary draft, renders it, and returns the image to the assistant. The draft is not put into the normal visualization feed. Once the assistant is satisfied, it can promote the same validated draft through show(draft_id=...) instead of recreating it.

This is more than a convenience feature. It gives the assistant a practical visual review loop. It can notice clipped labels, unsuitable chart types, unreadable legends, missing titles, crowded layouts, or a dashboard that does not fit in the initial viewport before the user sees it.

Earlier in the project, PR #12 made the two rendering choices clearer by renaming jupyter and panel to inline and server. inline represents a simple rendered result, while server represents a live Panel application. This distinction matters in the screenshot path because server applications may require a running local view before they can be inspected.

  • PR #20 made browser installation a supported CLI operation, so screenshots work for installed PyPI, uv, pip, and Pixi users, not only development environments.
  • PR #51 added private draft rendering and draft promotion to prevent double publishing.
  • PR #61 made screenshots capture full scrollable content and multiple dashboard pages, reporting when content remains outside the capture instead of silently pretending it saw the whole application.
2.2 / PANEL APPLICATIONS

I designed the screenshot system around real Panel applications

Panel Live Server supports both simple inline results and running Panel server applications. The screenshot feature therefore has to handle more than one static chart. It starts a local Panel view when necessary, uses Playwright Chromium to capture the rendered browser output, and returns either one image or a labelled set of images.

For PR #61, I added behaviour for dashboards that are taller than a browser window and dashboards with more than one page. This matters for practical data applications, where the first viewport may show only a title, a filter, or the first tab. The implementation supports Panel Tabs and common user-built page switchers, with targeted unit tests and browser UI tests.

2.3 / MEASUREMENT

I measured model-context cost and changed the design when the measurement disagreed with the first solution

Claude Desktop could not display a localhost iframe because of its content security policy. In PR #13, I implemented an inline HTML fallback using iframe.srcdoc. This allowed charts to appear inside Claude Desktop and gave interactive applications a browser-link fallback.

Later, I added payload token reporting in PR #46. The result showed that sending a complete rendered HTML page to the model was expensive and generally not useful to the model. For a simple chart, the embedded page could use around 14,000 tokens, compared with around 275 tokens for a normal result.

I used that evidence to change the design in PR #47. Claude Desktop and Cowork now use an explicit Open in browser action. This gives up an in-chat preview for those clients in exchange for a much smaller and more sustainable context footprint. Cursor and VS Code remain unchanged. I learned to solve a compatibility problem, instrument the result, measure real cost, and revise the solution when necessary.

2.4 / CORRECTION LOOP

I changed failures into a correction loop instead of a dead end

In PR #24, I merged the old two-step validate() then show() interaction into show(). The server now validates automatically before rendering. If validation or rendering fails, the tool returns a concise retry payload that explains the relevant problem and the result interface enters a “Refining visualization…” state.

The server does not independently rewrite a user's code. Instead, it turns a failure into structured feedback that the calling assistant can act on. Combined with the screenshot draft loop, this gives an MCP client two complementary ways to improve an answer before presenting it: code and runtime feedback when execution fails, and visual feedback when execution succeeds but the result is not good enough.

I improved this debugging path further in PR #35. The interface presents a short error summary first and keeps the full traceback in a collapsed disclosure. The traceback is inserted through textContent, which prevents code or error text from being treated as HTML.

2.5 / RELIABILITY

I made cross-environment execution reliable

Panel Live Server launches a local Panel server and executes user-provided visualization code in that environment. A fixed default port caused a subtle failure when users had more than one Python environment. A command from one environment could find an existing server on the shared port and reuse it even if that server belonged to another environment. The visualization then ran with the wrong installed packages.

In PR #42, I made the default Panel port deterministic per Python interpreter. The same environment can still reuse its own running server, but another environment receives a different port. PANEL_LIVE_SERVER_PORT remains an override for users who need a specific port. I tested this with packages installed only in separate environments, reproducing the issue in a way unit tests alone would not have shown.

I also fixed a separate concurrency issue in PR #49. Background validation runs code to detect runtime errors before display. Bokeh document state can otherwise be shared with an active browser session, so validation could occasionally write into the wrong document and fail with a pending-writes error. I gave the validation thread an isolated temporary document through Panel's per-thread state. Finally, PR #59 removed importlib from the blocked-import list, restoring package-availability checks used during evaluation, display, and screenshots.

2.6 / RESULT INTERFACE

I improved the rendered-result interface

  • PR #21 increased the default iframe height and changed the default zoom to 75 percent.
  • PR #35 added a concise error summary and a collapsible, safely inserted traceback.
  • PR #36 added a View Code interface with copy and return-to-visualization controls.
  • PR #39 added drag-to-resize support for the visualization iframe.
  • PR #40 added Python syntax highlighting to the code view.
2.7 / CONFIGURABLE PROMPTS

I made AI instructions configurable

In PR #52, I added pls mcp --prompts, allowing users and teams to provide a JSON file with custom instructions. The initial version supported library-selection and output guidance, with append and replacement behaviour.

In PR #54, I expanded this to cover all instruction sections, including introductory text, workflow, file policy, rendering guidance, errors, and screenshot guidance. Default behaviour remains unchanged when no custom prompts file is supplied.

2.8 / MCP INSTALLATION

I improved MCP installation and client support

I made setup easier for users who do not want to manually edit MCP configuration files. In PR #67, I added pls install <client> for Claude Desktop, Cursor, VS Code, and Claude Code. The command finds the active pls executable and writes the appropriate MCP configuration while preserving existing settings.

In PR #71, I expanded this from four to fourteen supported clients. It adds Windsurf, Cline, Junie, Gemini CLI, Google Antigravity, Kiro, GitHub Copilot CLI, Kilo Code, OpenAI Codex CLI, and Mistral Vibe. It also fixes config-path issues found while testing the clients and preserves user-managed configuration fields rather than replacing them.

MCP clients use different locations, configuration schemas, and file formats. Some use JSON with an mcpServers mapping, Kilo Code uses JSONC and a command array, and Codex and Mistral Vibe use TOML in different shapes. The implementation handles these formats separately where necessary, keeps other configured servers intact, preserves user-owned fields such as custom environment variables or timeouts, and is idempotent when the command is run twice.

2.9 / PERFORMANCE & QUALITY

I improved performance and code-quality enforcement

In PR #15, I removed redundant validation from the MCP display path. In PR #55, I measured lazy imports across the source and test suite. Imports with no meaningful startup cost were moved to module level, while expensive imports such as Panel, Bokeh, Pandas, Playwright, and server modules remained lazy.

In PR #69, I enabled Ruff's PLC0415 rule so non-top-level imports are visible during linting rather than only during review. Deliberately lazy imports are documented with a targeted noqa and a reason. In PR #72, I followed up on review feedback by allowing grouped imports where they improve readability, removing a temporary lint exception, and applying the resulting formatting consistently across the codebase.

2.10 / DOCUMENTATION & COMMUNITY

I improved documentation and contributor guidance

Documentation was a continuous part of my work. I wrote and revised setup, installation, architecture, MCP, and contributor documentation in PR #14, PR #16, PR #19, PR #32, PR #65, and PR #66. This work covers setup for multiple clients, MCP tools, cross-platform guidance, server configuration, deployment, custom AI instructions, troubleshooting, and HoloViz development skills.

I also wrote the public Panel Live Server blog post for the HoloViz blog. The accompanying HoloViz blog PR #101 was merged. The blog explains the project to a wider audience and complements the repository documentation.

Challenges and lessons learned

Building the product also meant revising earlier answers.

The project involved more than adding features. Several important changes came from measuring real behaviour, finding a limitation, and changing the design.

The Claude Desktop iframe limitation taught me that MCP clients can have materially different rendering restrictions even when they use the same server. The inline HTML workaround solved the visual problem, but token measurements showed that it was too expensive. Removing the embed for affected clients was a better outcome for practical use.

The environment-port and Bokeh-document fixes taught me that local development assumptions do not always hold when users run multiple environments, long conversations, or background validation. These issues were not obvious from the happy path, so I focused on reproducing the actual failure mode and adding targeted tests where possible.

I also learned that installation UX is part of the product. Supporting many MCP clients is not only a matter of writing JSON. Clients use different paths, configuration schemas, environment variables, TOML or JSON formats, and behaviours for existing settings. The installation work therefore emphasizes preserving existing configuration, idempotency, and tests for each format.
